# Версионирование протокола AFB ↔ BF

Здесь два независимых уровня версий. Не путать.

## 1. Версия провода — `protocol`

Значение поля конверта `protocol`, сейчас `afb.execution.v1`. Это **контракт
совместимости на проводе**. Меняется (`v1` → `v2`) только при несовместимом
изменении формата конверта или семантики, при котором старый и новый получатель
не могут договориться. Обе стороны на сессии обязаны использовать одну версию
провода (проверяется при handshake и в `validate_envelope_fields`).

## 2. Версия пакета/спеки — semver git-тег

Тег вида `vX.Y.Z` (например `v1.0.0`), он же `__version__` пакета и
`info.version` в `spec/asyncapi.yaml`. AFB и BF пинят зависимость по тегу:

```
afb-bf-protocol @ git+https://github.com/Rolo837/AFB-BF-protocol.git@v1.0.0
```

**⚠️ MAJOR запрещён по умолчанию.** Поднимать MAJOR-версию (`v1.x → v2.0.0`)
запрещено без явной специальной команды пользователя — независимо от того,
насколько изменение формально несовместимо. Если задача требует несовместимого
изменения (удаление/переименование типа или поля, новое обязательное поле,
смена семантики), работа над этим изменением не выполняется без отдельного
разрешения пользователя на MAJOR; вместо этого нужно искать обратносовместимый
путь (новое опциональное поле вместо переименования обязательного, новый тип
вместо изменения семантики старого и т.п.).

Правила инкремента:

| Уровень | Когда | Действие потребителя |
|---------|-------|----------------------|
| **PATCH** (`v1.x.y → v1.x.(y+1)`) | Доки, исправления схем/кода без изменения формата на проводе; **любые расширения протокола, не пересекающие канал AFB↔BF** — в т.ч. схемы/конвенции, специфичные для связки фронтенд↔бэкенд AFB (например `notification.*.vN.json`: они не входят в `spec/asyncapi.yaml`, не подписываются и никогда не пересекают канал AFB↔BF). **Для afbws-схем, не входящих в `spec/asyncapi.yaml`, удаление и переименование типов и полей — тоже PATCH**: строка MAJOR ниже и §4 говорят только о типах провода `afb.execution.v1`, а обе стороны такой схемы (backend AFB и фронтенд AFB) релизятся одним артефактом и обновляются одновременно | безопасно обновиться |
| **MINOR** (`v1.x.y → v1.(x+1).0`) | Обратносовместимое изменение протокола **AFB↔BF**: новый тип сообщения, новое **опциональное** поле, новый enum-вариант для исходящих — не ломающее взаимодействие с существующими BF | безопасно обновиться; новые возможности опциональны |
| **MAJOR** (`v1.x → v2.0.0`) | Несовместимое изменение **типов провода `afb.execution.v1`** (то, что описано в `spec/asyncapi.yaml`): удаление/переименование типа или поля, новое обязательное поле, смена семантики; обычно вместе с новым `protocol` `vN`. **Запрещено без специальной команды пользователя** (см. выше) | требуется согласованное обновление обеих сторон |

**Связь уровней:** смена версии провода (`afb.execution.vN`) всегда влечёт MAJOR
пакета — то есть возможна только вместе с явно разрешённым MAJOR. MAJOR пакета
не обязательно меняет версию провода (например, удаление давно депрекейтнутого
типа в рамках того же `v1`), но всё равно требует разрешения.

## 3. Совместимость сторон

- AFB и BF должны быть на одной **MAJOR** версии пакета.
- В пределах одной MAJOR более новая сторона обязана понимать сообщения от более
  старой (forward/backward в рамках MINOR/PATCH).
- Источник истины статусов сделки — AFB; источник истины о состоянии у брокера —
  BF (см. `docs/` и `spec/`).

## 4. Депрекейт типов сообщений

Этот раздел относится к **типам провода `afb.execution.v1`** — тем, что описаны в
`spec/asyncapi.yaml` и пересекают канал AFB↔BF. Схемы, которые в AsyncAPI не
входят (например `afbws/*.channel.v1.json` и `notification.*.vN.json`), живут по
правилу PATCH из §2: удалять и переименовывать в них можно сразу, без цикла
депрекейта, потому что обе стороны такой схемы деплоятся вместе.

1. Пометить сообщение в `spec/asyncapi.yaml` тегом `deprecated` и описать замену
   в `summary`/`description`. (Прецедент миграции имён: `bf.*`/`execution_deal.*`
   → `session.*`/`deal.*`.)
2. Релиз MINOR: тип ещё принимается, но помечен; обе стороны переводятся на
   замену.
3. Удаление типа — только в следующем **MAJOR** (запрещён по умолчанию, см. §2 —
   нужна отдельная команда пользователя), после того как обе стороны перестали
   его слать (подтверждается журналами `trading_events`).

**Текущие депрекейты** (тег `deprecated` в `spec/asyncapi.yaml`, введены v2.3.0):

| Тип | Замена |
|-----|--------|
| `broker.get_account` | `broker.get_accounts` |
| `broker.account` | `broker.accounts` |
| `broker.get_instrument` | `broker.resolve_instrument` |
| `broker.instrument` | `broker.instrument_resolved` |

Все четыре остаются в `MESSAGE_REGISTRY`/`COMMAND_TYPES`/`BF_EVENT_TYPES` — депрекейт не
удаление. Первая пара шлётся только между сторонами, не согласовавшими
`features.multi_account`; вторая — не отправляется ни одной актуальной стороной, оставлена
для совместимости со старым BF/AFB.

## 5. Модель веток и процедура релиза

С введения ветки `develop` (см. `run/README.md`) версия **не** поднимается
покоммитно. Разработка идёт на `develop`; потребители в режиме разработки пинят
`@develop` (AFB — `AFB/requirements.txt`, `AFB/informer/requirements.txt`,
`AFB/frontend/package.json`). Настоящий тег `vX.Y.Z` и merge `develop→main`
происходят **как часть релиза AFB** — единый комплекс `AFB/run/release.sh`
вызывает здешние `run/version.sh` и `run/release.sh`.

Канон semver-версии — корневой файл `VERSION`; `run/version.sh` синхронизирует его
с четырьмя местами (`python/pyproject.toml`, `python/afb_bf_protocol/version.py`,
`spec/asyncapi.yaml` `info.version`, `package.json`), `run/check-version.sh`
проверяет синхрон.

### Разработка (на `develop`, без версии)

1. Изменить `spec/asyncapi.yaml` и/или `spec/schemas/*` (канон).
2. `afb-bf-protocol-generate` — перегенерировать `taxonomy.py`, `docs/` и
   `ts/src/taxonomy.ts` + `ts/src/index.ts` (и `ts/src/models.ts` +
   `python/afb_bf_protocol/models_generated.py`, если доступны Node и
   `datamodel-code-generator` — см. `generate_pymodels()` в `tools/generate.py`).
3. `python -m afb_bf_protocol.tools.make_fixtures` — обновить примеры при
   изменении формата.
4. `pytest` + `npx @asyncapi/cli validate spec/asyncapi.yaml` + `npm run typecheck`
   — зелёные.
5. Commit в `develop`, push. Локальные сборки AFB (`AFB/run/build.sh`) сразу
   подхватывают новый `@develop`.

Записи об изменениях протокола дописываются в `CHANGELOG.md` в секцию
`## Unreleased` **сразу по ходу работы, без версии и даты**. `run/version.sh`
(→ `stamp_changelog`) сам оформит их под `## vX.Y.Z — YYYY-MM-DD` и заведёт новую
пустую `## Unreleased`. Никаких `.draft`-файлов и проверок «секция обязана быть».

### Релиз (обычно из `AFB/run/release.sh tag --protocol {patch|minor}`)

6. `run/version.sh {patch|minor}` — поднять версию в `VERSION` + 4 местах, оформить
   `## Unreleased` под `vX.Y.Z`, commit `release vX.Y.Z`.
7. `run/release.sh tag` — аннотированный тег `vX.Y.Z` на `develop`, push тега.
   Потребители (комплекс AFB) пинят `@vX.Y.Z` для воспроизводимых образов.
8. После soak — `run/release.sh publish`: PR/merge `develop→main`, GitHub Release
   (`--generate-notes`), синхронизация `develop` с `main`.
